# Dashboard 内容设计（草案 v1）

## 读者与一句话目标
读者：PostHog 的工程负责人，忙，懂工程，不会逐条读 PR。
首屏 10 秒内回答："过去 90 天最有影响力的 5 位工程师是谁、各自凭什么"；任何数字点一下就能看到怎么算的、证据是哪几条 PR。

## 评估标准 → 页面上的落点

| 评估标准 / 红线 | 页面怎么满足 |
|---|---|
| 一眼理解 | 首屏只有 Top 5 卡片 + 一行"影响力定义" + 一行数据覆盖；卡片上是角色标签和一句话理由，不是总分 |
| 能验证结论 | 每个数字可展开：公式、原值、候选内百分位、证据 PR 链接；页脚给数据快照与代码仓库链接 |
| 有效、清晰 | 静态页 + 预计算 JSON（目标 < 1.5 MB），无后端；首屏渲染不依赖展开区的数据 |
| 方法与理由清晰 | 折叠区"我们怎么衡量"：漏斗图（208 → 82 → 20 → 5）+ 每阶段标准 + 档位表 |
| 实用主义 | 方法区写明取舍：哪些信号因成本只对 20 人计算、哪些被排除及原因 |
| 数据不完整 | 覆盖条：18,715 条合并 PR，121 天逐日核对与 GitHub 计数一致；排除项（bot、AI agent 代开 PR）的数量写明 |
| 数字无法理解 | 不出现裸总分；等级旁边总有锚点说明（9–10 公司级关键 …），百分位旁边总有原值 |

## 页面结构（笔记本一屏 1440×900 为首屏基准）

### A. 页头（一行）
标题 · 窗口 2026-08-05 → 2026-11-03 · 覆盖："18,715 merged PRs · 204 engineers · bots & AI-agent PRs excluded" · 一句话定义："Impact = durable change to PostHog's product, systems and team, traceable to specific PRs, judged by quality and importance over volume."

### B. Top 5（首屏主体）
五张横排卡片（窄屏改为纵向），每张：
- 名次、姓名 + GitHub handle、团队
- **角色标签**（类型）：如 "Platform builder · Query engine"
- **一句话理由**（来自 L4 的 top5_cases）
- **四角度迷你条**：交付 / 系统 / 质量 / 团队，各 1–10 级，悬停显示锚点含义
- **3 个关键数字**（每张卡由 L3 选出最能代表此人的 3 个，带指标键）：例如"4 major workstreams"、"trusted approver for 3 teams"、"0 reverts in 61 PRs"
- 稳健性徽章：稳定 / 边界，以及"两次独立决策均入选"
点击卡片 → 打开 C 区该人的详情（同页面右侧抽屉或卡片下方展开）。

### C. 候选人详情（展开）
1. 定位（一句话）+ 影响方式
2. **核心贡献**：2–3 条工作流，每条：标题、做了什么、为什么重要、结果、他的角色、时间跨度、代表 PR（链接 + 一句话摘要 + 档位）
3. **团队中的位置**：网络摘要一段 + 指标小表（首轮通过率、被请求评审人数、批准覆盖团队数、继续开发其代码的作者数、修复他人 vs 被修复）
4. **核心特征（自定义分析）**：L3 的 custom_analyses，每条：问题 → 发现 → 证据
5. **定量明细**（折叠）：四角度 × 三类证据表，原值 + 百分位 + 定义；档位分布条；片段数；AI 协作占比
6. **反证与风险**：counter_evidence、red_flags、覆盖率
7. 全部 PR 列表（折叠，按工作流分组，可按档位筛选）

### D. 第 6–10 名（一行一人）
姓名、角色标签、一句话、"为什么没进前 5"（L4 的 sixth_place_note 与比较理由）。

### E. 折叠区（页面下方，默认收起）
1. **我们怎么衡量**：漏斗示意 + 每阶段数量与标准 + 档位表（1-2-4-8-16）+ 片段规则 + 四角度权重 + 决策流程（L3 → L4 ×2 → 魔鬼代言人 → 门槛）
2. **召回统计**：208 人 → 139 过门槛 → 82 召回；各召回路线命中人数与独占人数；漏召审计结果
3. **粗排统计**：分诊档位分布（全体 / 候选）；前 20 的表（重要性总量、各档条数、质量率、团队分、粗排分、入选路线），可排序
4. **团队网络**：社区与官网团队对照、桥接者前 10、单点依赖区域；可选一张小网络图（只画前 40 人）
5. **比较矩阵**：20 人 × 14 列，可排序，列头悬停看定义
6. **数据与验证**：逐日抓取核对、bot 与 AI PR 排除数、LLM 调用数 / 错误率 / 费用、引文核对失败率、两次决策一致度、权重敏感性
7. **局限**：90 天窗口、功能分支 PR 的谱系缺口、PostHog 极少使用"要求修改"、LLM 判断的不确定性

## 数据产物
`out_full/site_data.json`（由 `impact/site_data.py` 从各阶段输出生成）：
`{meta{window, fetched_at, coverage, exclusions, cost}, top5[...], next5[...], candidates{login: detail}, funnel{recall_stats, route_hits, audit}, coarse_table[...], tier_distribution, team{communities, bridges, single_points}, matrix{columns, rows}, validation{...}, definitions{metric_key: {label, formula, source}}}`
`definitions` 是所有指标键的唯一说明来源，页面上任何数字的悬停与展开都从这里取。

## 不做
登录、后端、实时数据、多页面路由、复杂可视化动效。

## F. 团队协作网络图（用户 2026-11-03）

目的：直观看出谁是团队网络的核心节点，并且能顺着边看到具体 PR。

### 节点 = 人
- 入图：精排 20 人 + 重要性回流（importance_flow）前 40 + 桥接者前 10 + 各社区评审枢纽，去重后上限 60。
- 大小 = 重要性回流分（结合了 PR 档位与评审回流）；颜色 = 评审网络社区（图例写主要团队名）；Top 5 加粗外环并标名次；其余 20 名候选细外环。
- 悬停/点击：姓名、handle（链接到 GitHub 主页）、团队、角色标签、3 个关键数字（PR 数、重大及以上片段数、首轮通过率）、候选人详情锚点（如有）。

### 边 = 两人之间的关系（按类型聚合）
| 类型 | 方向 | 样式 | 权重 |
|---|---|---|---|
| 评审（批准 / 评论 / 要求修改） | 评审者 → 作者 | 蓝灰实线 | 涉及 PR 的点数之和 |
| 继续开发 | 后来者 → 原作者 | 绿色实线 | 涉及 PR 的点数之和 |
| 修复 / 回退 | 修复者 → 原作者 | 红色虚线 | 次数 |
- 点击边：列出底层 PR（≤10 条，按点数降序）：PR 号链接、标题、档位、事件类型、日期。

### 信息量与缩放（语义缩放）
- **总览**（默认）：≤60 节点、≤150 条边（每类按权重取前若干，阈值滑块可调）；只给 Top 20 标名字；社区背景色块 + 团队标签。
- **放大**：缩放超过阈值后，所有节点显示名字，边显示权重。
- **聚焦**（点击某人）：只保留此人及其一跳邻居（可超出总览的 60 人，上限 30 个邻居），其余淡化；侧栏显示此人的关系列表（谁评审他、他评审谁、谁在他代码上继续开发），每条关系可展开到 PR。
- 控件：边类型开关、权重阈值、"只看 Top 20"、重置视图。

### 实现
- 布局由 Python 预计算（networkx spring_layout，按社区初始化，seed 固定），前端不跑力导向，打开即稳定。
- 前端：cytoscape.js（固定版本，cdnjs）；数据 `site/network_data.json`（目标 < 300KB）。
- 位置：主页面 E 区"团队网络"展开后嵌入；也可单独打开 `site/network.html`。

## G. v2 视觉与信息组织重构（用户 2026-11-03）
- **深色风格**，与团队网络图（starmap 风格）统一：同一套深色底、强调色、字体与卡片质感；网络图嵌入时不再需要额外深色外框。
- **Top 5 候选人卡片**重排为四块，从上到下：
  1. 名次 + 姓名/handle + 团队 + **角色标签**（大字，一眼可读）
  2. **要点**：2–3 条核心贡献，每条一行（工作流标题 + 一句结果），来自 L3 core_contributions
  3. **关键数据**：3 个数字大字展示（key_numbers），每个带小标签与百分位
  4. **打分**：四角度 1–10 迷你条 + 综合等级 + 稳健性徽章
  卡片点击打开详情抽屉（不变）。
- **下方"排名是怎么来的"区**：不再是平级的折叠列表，改为**卡片网格**（桌面 3–4 列）。每张卡片 = 图标 + 标题 + 1–2 个关键数字 + 一句话；点击打开大号弹层（modal）查看细节（原折叠区的全部内容搬进弹层）。卡片示例：
  - 漏斗图标 · "How we measure" · `208 → 82 → 20 → 5`
  - 召回 · `82 recalled · 5 routes`
  - 粗排 · `15,473 PRs triaged · 0 errors`
  - 团队网络 · `204 people · 14 communities`（弹层内嵌网络图）
  - 比较矩阵 · `20 × 14`
  - 数据与验证 · `18,715 PRs · 121/121 days reconciled`
  - 局限 · `N caveats`
  - 第 6–10 名也做成同样的卡片行（每人一张小卡：角色 + 一句话 + 为什么没进前 5）
- 图标用内联 SVG（不引入图标库）；弹层可键盘关闭（Esc），焦点管理正确。

## H. 卡片关键数据 = 原始事实，不是加权分（用户 2026-11-03）
- 卡片上的 3 个关键数据只用**可直接核对的原始事实**：PR 数、被评为重大/里程碑的 PR 数、revert 数与比例、被他人跟进修复的比例、首轮通过率、给他人的评审数与服务人数、点名请他评审的人数、在他代码上继续开发的作者数、changelog 收录数、关闭的 issue 数、批准覆盖的团队数、活跃周数（x/13）。加权分（交付点数、团队杠杆分、PageRank）只在详情抽屉里出现，并附公式。
- 每个数据配一个**特征标签**，用数据说明这个人的特色，例如：
  - "0 reverts in 246 PRs · 98% first-pass approval" → High-quality shipper
  - "Approved PRs from 48 authors across 21 teams" → Review backbone
  - "106 engineers later built on his files" → Foundation builder
  - "46 changelog entries" → User-visible shipper
- 选法：从上面的原始事实中，选此人在 20 人中百分位最高、且彼此不重复维度的 3 个；特征标签由规则映射，L3 的 archetype 作为卡片标题角色。
