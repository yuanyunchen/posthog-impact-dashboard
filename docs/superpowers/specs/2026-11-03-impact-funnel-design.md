# PostHog 工程师影响力评估：漏斗与系统设计（草案 v4）

状态：讨论中，未经用户批准。带 ≈ 的数量为调研估计，待数据画像（T01.02/S02）核实。
v4 改动：档位分值改为 1-2-4-8-16（五档，机械类 0 分不计），PR 影响点改为 P = 2^(4ℓ/3)，与档位同一量纲（用户 2026-11-03）。v3 改动：新增第 9 节打分与决策机制（取代第 2 节末的参考分公式）。v2 改动：评估角度收敛为 4 个，每个角度用同一套三类证据评估；漏斗简化为召回 → 粗排 → 精排。

## 1. 影响力定义

影响力 = 评估窗口（2026-08-05 → 2026-11-03，90 天）内，一位工程师的工作给 PostHog 带来的、能追溯到具体变更的持久改变。

原则：
1. 重要性与质量优先于数量，且非线性：一条重大改动 ≫ 多条次要改动。
2. 每个结论都由三类证据支撑：**定量数据**（脚本算的）、**agent 评估**（读 PR 后的判断）、**行为关联**（同事用行动做出的评价）。
3. 分数只作参考，最终排序由裁决 agent 综合判断，必须引用数据和实例。

## 2. 四个评估角度

| 角度 | 参考权重 | 低分 → 高分 | 定量数据 | agent 评估 | 行为关联（他人行动） |
|---|---|---|---|---|---|
| **交付重要性** | 50% | 局部便利 → 改善工作流 → 解锁重要能力或解决重大用户问题 | 非线性档位累计（机械 0；微小 1 / 常规 2 / 实质 4 / 重大 8 / 里程碑 16） | 深读 PR：用户价值、关键性（故障、数据正确性、安全、计费）、创新 | changelog 收录；关闭 issue 的用户点赞数 |
| **系统杠杆** | 20% | 一次性局部收益 → 可复用改进 → 持续降低多个团队的成本或风险 | 核心路径占比；热点文件占比 | 深读 PR：是否是抽象、平台、工具、性能或架构改进 | 他改过或新建的代码，随后被多少其他作者继续修改或引用 |
| **工程质量** | 15% | 返工多、被回退 → 稳定交付 | revert 率；14 天内被他人跟进修复率；测试改动占比 | 深读 PR：设计清晰度、风险控制 | 被 revert、被他人修复；评审中被要求修改的轮数 |
| **团队杠杆** | 15% | 盖章式评审 → 评审改变了代码、被同事倚重 | 给他人的人类评审数、服务的不同作者数、首评时长 | 读他的 10 条评审评论：是否抓到真问题 | 评论所在行之后被改的比例；**被多少不同的人请求评审** |

参考分 = 各角度在候选人中的百分位 × 参考权重。参考分进入评估卡，但不直接决定排名。

非线性的两处落点：
- 粗排的档位分值按倍数增长（1-2-4-8-16）：一条重大 = 4 条常规，一条里程碑 = 16 条微小。
- 精排用分层估计：个人交付 = Σ（该档条数 × 该档深读均分）。数量只在同档内累加。

## 4. 评估卡结构（精排产物）

## 9. 打分与决策机制（v3）

### 9.1 PR 层

**分诊（粗排，Flash，候选人全部 PR）**——定档锚点：

| 档 | 分值 | 判定标准 |
|---|---|---|
| 机械 | 0（不计） | 依赖升级、生成代码、lockfile/快照、重命名、纯配置开关、纯 revert |
| 微小 | 1 | 文案、样式、一两行的局部修正 |
| 常规 | 2 | 单模块内的小修复或小功能调整，用户几乎无感 |
| 实质 | 4 | 用户可感知的功能增量或有意义的修复；或团队内可复用的改进 |
| 重大 | 8 | 新能力或新产品面；修复事故、数据正确性、安全、计费问题；跨团队平台或性能改动 |
| 里程碑 | 16 | 公司级新产品或架构级变革，多个团队受益 |

规则护栏：改动全部落在降权路径 → 强制机械；非生成改动 <10 行却判重大 → 必须给出引文，否则降为实质。

**深读（精排，Flash，分层抽样 ≈15 条/人）**——四个子维度，每项必须附原文引文，引文核对不通过则该项减 1：

| 子维度 | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| V 用户/业务价值 | 无外部价值 | 局部便利 | 明确改善工作流 | 解锁重要能力或解决重大用户问题 |
| C 关键性 | 可延后 | 小影响 | 明显阻塞 | 核心运行、数据正确性或安全 |
| N 创新 | 常规实现 | 有效新组合 | 解决原方案难解的问题 | — |
| L 系统杠杆 | 一次性 | 局部复用 | 可复用改进 | 持续降低多个团队的成本或风险 |
| Q 质量 | 有明显风险或缺测试 | 合格 | 设计清晰、测试与风险控制到位 | — |

PR 重要性等级 ℓ = 0.55·V + 0.30·C + 0.15·(1.5·N)，范围 0–3。
PR 影响点 P = 2^(4ℓ/3)：ℓ=0 → 1，ℓ=0.75 → 2，ℓ=1.5 → 4，ℓ=2.25 → 8，ℓ=3 → 16，与分诊档位同一量纲（1-2-4-8-16），分层估计可直接混用。

### 9.2 人层：四个角度，每个角度三类证据

每类证据在 20 名候选人中转为百分位（0–100）；角度分 = 三类证据的等权平均；缺失项记 50 并标注。

| 角度（参考权重） | 定量数据 | agent 评估 | 行为关联 |
|---|---|---|---|
| 交付重要性（50%） | 交付量 = Σ_档 (该档条数 × 该档深读平均 P)；未深读档用档位分值 | 评估 agent 对其最重要 3 项贡献打 1–10 | changelog 收录的 PR 数（按档加权）+ 所关闭 issue 的 👍 总数 |
| 系统杠杆（20%） | 交付量中落在核心路径的占比 | 深读 PR 的 L 均值（按 P 加权） | 下游作者数：他新建或改动 ≥20 行的文件，之后被多少名其他作者修改 |
| 工程质量（15%） | 1 − (被 revert 数 + 14 天内被他人跟进修复数) / 实质及以上 PR 数 | 深读 PR 的 Q 均值 | 人类评审 CHANGES_REQUESTED 的平均轮数（越低越好，反向百分位） |
| 团队杠杆（15%） | 给他人的人类评审数 × log(服务的不同作者数) | 评估 agent 读其 10 条实质评审评论，打 1–10 | 评论所在行之后被改的比例 + 被不同的人请求评审的人数 |

参考总分 R = 0.50·交付 + 0.20·系统 + 0.15·质量 + 0.15·团队（0–100）。

### 9.3 评估 agent（每人一张评估卡）
- 输入：证据档案、深读结果、参考分（四个角度及 R）。
- 输出：四个角度各给 1–10 级。锚点：9–10 公司级关键或多团队受益；7–8 团队核心支柱；5–6 稳定的有效贡献；3–4 局部贡献；1–2 边缘。每个等级至少引用 2 个数据点和 1 个 PR 链接。
- 再给综合 1–10、置信度、反证与风险。
- 约束：某个角度的等级与参考百分位档（百分位 / 10）相差 >3 时，必须写明理由。

### 9.4 最终决策
1. **独立排序**：3 个排序 agent 各读 20 张评估卡（姓名替换为编号，避免名气偏差），各自给出前 10 名和理由。
2. **两两裁决**：3 个排序结果中名次有分歧、且落在第 3–8 名的人两两比较，每对交换顺序各问一次；两次一致才算胜，否则记平。
3. **汇总**：Borda 计分（第 1 名 10 分 … 第 10 名 1 分，3 人求和），平分时用两两裁决结果打破。
4. **魔鬼代言人**：对暂定 Top 5 每人写出"最强的反对理由"和"最可能替代他的人"；manager 逐条回应，决定保留或替换，并写进记录。
5. **入选门槛**（任一不满足须单独论证，否则替换）：(a) ≥2 条重大档 PR，或团队杠杆位列候选前 3；(b) 无未解释的质量红旗（被 revert ≥3 次，或跟进修复率处于候选最差 20%）；(c) 至少 2/3 的排序 agent 将其列入前 7。
6. **稳健性标注**：参考权重各自在 ±50% 内随机扰动 1000 次，统计每人按 R 进入前 5 的频率：≥70% 稳定，40–70% 边界，<40% 仅裁决入选（必须有论证）。
7. 与用户讨论后定稿。看板对每人展示：四个角度的分数（可展开为三类证据）、综合等级、稳健性标签、3 条证据 PR、一句话理由。

## 10. 精排的层级结构（v5，用户 2026-11-03）

精排不只看 PR：PR 打分是底层定量参考，向上逐层抽象为工作流、角色与整体贡献，顶层做有洞见的比较判断。顶层不读原始数据。

| 层 | 执行者 | 输入 | 产出 | 抽象程度 |
|---|---|---|---|---|
| L0 规则统计 | 脚本 | PR、评审、git 谱系 | 个人指标表、比较矩阵（原值 + 候选内百分位） | 原始数字 |
| L1 PR 评估 | Flash | 单条 PR 的 diff、正文、评审 | 档位、五项分、P、一句话摘要、原文引文 | 单个改动 |
| L2 工作流归纳 | Flash（每个工作流一次） | 一个人的片段按产品区与主题聚成 3–8 个工作流，含各 PR 的 L1 结果 | 每个工作流：做了什么、为什么重要、结果、他的角色（主导/参与/评审）、合作者、聚合分数、代表 PR | 一段持续工作 |
| L2' 角色画像 | 脚本 | 评审网络、团队映射、知识归属 | 他评审谁、被谁评审、跨团队桥接度、所在区域的主要维护者身份 | 团队位置 |
| L3 候选人评估 | Claude（每人一个） | L2 全部工作流 + L2' 角色画像 + L0 摘要 + 少量 L1 样例 | 候选人报告：定位一句话、核心贡献（2–3 个工作流）、影响方式、四角度定级、反证与不确定性、非显而易见的洞察 | 整体贡献 |
| L4 总决策 | Claude | 20 份 L3 报告 + L0 比较矩阵 | 排序、分组比较（同类候选人之间的取舍）、每位 Top 5 的论证、对第 6 名的说明 | 横向比较 |

L4 的校验：第二个独立决策 agent 盲排一次，用于一致性检查；魔鬼代言人对 Top 5 提出反驳；主 agent 定稿。分歧处由主 agent 按需下钻 L2/L1 取证据，再交回 L4，L4 本身不读原始数据。

### 减少逐层信息损失的规则
1. 每层上报固定结构：`claims[]`，每条 = 论断 + 数字 + 证据 ID（PR 号、工作流 ID、指标键），上层引用即可下钻。
2. 极值不平均：每层必须原样上报最重要的 3 项与全部红旗，不得被均值掩盖。
3. 数字走脚本、不走转述：比较矩阵由 L0 直接生成交给 L4，LLM 只负责解释，不负责搬运数字。
4. 每份报告带覆盖率与置信度：样本数、数据缺失项、diff 截断比例。
5. 下钻通道：L4 对边界比较可以列出"需要的证据"，由主 agent 从下层取回。

## 11. v6 修订：团队事件建模、L2 并入 L3、两级 PR 评估的分工（用户 2026-11-03）

### 11.1 团队事件图（亮点）
把窗口内全部人类 PR 的协作事件建成一张有向多重图，节点是人，边是事件：

| 事件 | 边 | 来源 |
|---|---|---|
| 批准 | 评审者 → 作者 | reviews.state=APPROVED（剔除 bot） |
| 要求修改 | 评审者 → 作者 | CHANGES_REQUESTED；评审后作者再提交 = 修改被采纳 |
| 评论 | 评审者 → 作者 | COMMENTED（正文长度 > 0） |
| 请求评审 | 请求者 → 被请求者 | ReviewRequestedEvent（仅 20 名精排候选相关 PR） |
| 回退 | 回退者 → 原作者 | 显式 revert |
| 跟进修复 | 修复者 → 原作者 | 显式引用的 fix |
| 继续开发 | 后来者 → 原作者 | 谱系：修改其窗口内改过的文件（排除枢纽文件） |

由图得到三类结论：
1. **个人在团队里的位置（脚本指标）**：首轮通过率（无要求修改即获批）、被要求修改率与平均轮数（需要别人纠正的程度）、给出的要求修改被采纳率（把关质量）、批准他人数与覆盖团队数、被请求评审的不同人数（信任需求）、继续开发其代码的作者数（地基）、修复他人问题 vs 被他人修复（救火 vs 制造工作）。
2. **信任加权**：批准边按批准者自身信任度加权（批准图上的 PageRank）——被高信任评审者一次通过的 PR 更有分量；重要性回流：以 PR 的 P 为种子，在 人–PR 图上传播，重要 PR 的作者与实质评审者都获得回流。
3. **团队整体结构**：在评审图上做社区划分，与官网团队映射对照；找出跨社区的桥接者（betweenness）、各社区的评审枢纽、单点依赖（某区域只有一人批准）。看板可展示一张协作网络小图。

产出 `out/team_graph.json`：每人一组网络指标（带指标键）+ 社区与桥接者列表 + 每个指标的定义。

### 11.2 层级关系与 L2 并入 L3
树为一对多：L4（1）→ L3 候选人（20）→ 工作流（每人 3–8，脚本聚类）→ PR（每流若干）→ L0 原始事件。
- **L2 只保留脚本聚类**：把片段按产品区与主题聚成工作流，附每条 PR 的 L1 摘要与聚合数字；不再单独调用 LLM 归纳。
- **工作流叙述由 L3 评估 agent 自己写**：它一次看全该候选人的工作流，归纳主线、判断角色，比逐流归纳少一层转述、少一次信息损失。

### 11.3 粗排与精排的 PR 评估分工

| | 粗排 L1 | 精排 L1 |
|---|---|---|
| 范围 | 60 人的全部 PR（≈7k） | 20 人，每人分层抽样 ≈19 条（≈380） |
| 输入 | 标题、正文、路径、标签 | 完整 diff（≤24k 字符）+ 评审讨论 |
| 输出 | 档位、标记、一句话摘要 | 档位复核、V/C/N/L/Q 五项分与原文引文、P、3–5 句摘要（做了什么、为什么、怎么做、风险） |
| 单价 | ≈$0.0003 | ≈$0.0015 |

L3 读的是 L1 摘要（深读样本用精排摘要，其余用粗排一句话）+ 工作流聚合 + 团队事件指标 + 指标摘要，**不读 PR 原文和 diff**。

## 12. v7 修订：粗排纯定量，精排为每位候选人一个 agentic 分析师（用户 2026-11-03）

- **粗排**：只做定量累加（档位分 → 片段分 → × 质量率 + 团队杠杆），不做定性判断。
- **精排 L3**：20 名候选人各一个独立 Claude 子智能体，做系统性、多角度、agentic 的分析：
  - **统一标准（必做）**：报告契约的全部章节——定位、2–3 条核心工作流叙述、团队中的位置、四角度定级（每项 claims 带数字与证据 ID）、红旗与反证、覆盖率。
  - **自由度（必做至少 2 项自定义分析）**：agent 根据该候选人的特点自行决定追问什么，例如：他的贡献是否集中在某次发布前后、他在哪个团队的评审里最有分量、他的 AI 协作产出质量如何、他是否在别人放弃的问题上接手解决。每项写明：为什么问、怎么查、发现了什么、对评估的影响。
  - **工具**：每位候选人一个数据包目录 `out/candidates/<login>/`（档案 markdown、工作流、网络位置、全部 PR 的 L1 摘要），以及查询命令 `python -m impact.fine.query <login> <子命令>`：按区域/档位/时间筛 PR、看单条 PR 的 L1 详情、他给出与收到的评审、周度时间线、某指标在 20 人中的位置、和另一位候选人对比；`deepread <n>` 可按需对未抽样的 PR 补一次 Flash 深读（每人上限 6 条）。
  - **边界**：不读 PR 原文和 diff（补深读的结果也只给摘要与分数）；所有自定义发现同样必须带证据 ID。
- **L4** 读 20 份报告 + 比较矩阵；L3 的自定义发现进入"洞察"栏，L4 在横向比较时引用。
